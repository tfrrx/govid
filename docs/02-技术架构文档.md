## 1. 架构总览

### 1.1 部署形态

单机单进程服务，前端静态产物由后端直接托管，**不依赖任何外部中间件**。

```
                        ┌───────────────────────────────┐
   浏览器（桌面/手机）   │   FastAPI 进程 :8000          │
  ┌──────────────┐      │                               │
  │  Vue 3 SPA   │◄────►│  /api/*      ← 接口层         │
  │  (静态产物)  │ HTTP │  /assets/*   ← 静态资源       │
  └──────────────┘      │  /*          ← SPA 兜底       │
                        │                               │
                        │  ┌─────────────────────────┐  │
                        │  │ 任务队列（内存字典）     │  │
                        │  │  + 线程池（信号量限流）  │  │
                        │  └───────────┬─────────────┘  │
                        │              │                │
                        │  ┌───────────▼─────────────┐  │
                        │  │ yt-dlp 封装（本地仓库）  │  │
                        │  └───────────┬─────────────┘  │
                        │              │                │
                        │  ┌───────────▼─────────────┐  │
                        │  │ ffmpeg（三级来源探测）   │  │
                        │  └─────────────────────────┘  │
                        └───────────────┬───────────────┘
                                        │ HTTPS
                                        ▼
                              ┌──────────────────┐
                              │  源站（B站/YT…)  │
                              └──────────────────┘
                         临时文件落盘：项目根 tmp/<task_id>/
```

### 1.2 分层与依赖方向

```
api/  ──────► core/  ──────► yt-dlp / 系统
  │             ▲
  └──► models/  │（models 不依赖任何内部模块）
                └─ core 之间允许互相调用，但 core 绝不 import api
```

**硬约束**：`core/` 不得反向依赖 `api/`。这样阶段 3 引入新的调用方（比如 AI 流水线）时，可以复用 core 而不必绕开 HTTP 层。

| ffmpeg | static-ffmpeg + imageio-ffmpeg | — | 见 §7.3 |

### 模块职责边界

| 模块 | 负责 | **不**负责 |
|------|------|-----------|
| `core/media.py` | 平台路由 + yt-dlp 的调用与结果整理 | 不碰 HTTP、不管并发、不实现具体平台 |
| `extractors/douyin/` | 抖音的解析与下载全流程 | 不感知任务队列、不做 HTTP 适配；浏览器只用于借签名 |
| `core/tasks.py` | 任务生命周期、进度、限流 | 不直接调 yt-dlp 或具体 extractor（通过 media） |
| `core/ffmpeg.py` | 探测与缓存 ffmpeg 位置 | 不执行转码（yt-dlp 自己调） |
| `core/errors.py` | 错误分类与中文文案 | 不决定 HTTP 状态码语义以外的事 |
| `api/*` | 参数校验、返回结构 | 不写业务逻辑 |
| `composables/useDownloader.js` | 前端状态机与轮询 | 不做 DOM 操作 |

> **扩展新平台时**：在 `extractors/` 下建同名子包，暴露 `is_<平台>(url)` 与 `parse` / `download` 三个函数，然后在 `core/media.py` 的路由处加一行判断即可。`tasks.py` / `api/` / 前端**全部零改动**。

## 4. 核心数据流

### 4.1 解析流程（POST /api/parse）

```
前端                    后端                         yt-dlp / 源站
 │
 │ POST {url}
 ├──────────────────────►│
 │                       │ 1. URL 格式校验 ──► 不合法 → InvalidURLError(中文)
 │                       │
 │                       │ 2. YoutubeDL(extract_flat=False).extract_info(download=False)
 │                       ├───────────────────────────►│
 │                       │                            │ 抓页面 / 调 API
 │                       │◄───────────────────────────┤ info dict
 │                       │
 │                       │ 3. build_formats(info)：按分辨率归组 + 合并选择器
 │                       │ 4. platform_name(info)：extractor → 中文站名
 │                       │
 │◄──────────────────────┤ 200 {title, thumbnail, duration, author,
 │                       │      platform, formats[]}
 │ 5. 渲染双列结果        │
 │    （封面走 /api/proxy/thumbnail）
```

**失败路径**：yt-dlp 抛出的任何异常都经 `errors.translate_error()` 转换为带中文 message 与 `code` 的业务异常，再由 `main.py` 的 `GoVidError` 处理器统一序列化为 `{detail, code}`。

### 4.2 下载流程（POST /api/tasks → 轮询 → GET file）

```
前端                     后端                         yt-dlp
 │
 │ POST {url, format_id, title, quality_label}
 ├───────────────────────►│
 │                        │ create_task()：登记内存字典，status=pending
 │◄───────────────────────┤ {task_id}   ← 立即返回，不等下载
 │                        │
 │                        │ 后台线程 _run_task → 信号量限流
 │                        │   acquire 到才进入 downloading
 │                        │  ├─ run_download()：yt-dlp 下载 + 合并
 │                        │  │    progress_hook ──► 按 format_id 分桶累加字节
 │                        │  │    postprocessor_hook ──► status=merging
 │                        │  └─ _resolve_output_file()：定位最终产物
 │                        │
 │ GET /api/tasks/{id} 每 1s
 ├───────────────────────►│
 │◄───────────────────────┤ {status, progress, speed, eta, …}
 │                        │
 │ [用户点取消]
 │ POST /api/tasks/{id}/cancel
 ├───────────────────────►│ 置 cancel 标志 ──► 下载线程抛 DownloadCancelled
 │◄───────────────────────┤ status=cancelled
 │
 │ GET /api/tasks/{id}/file
 ├───────────────────────►│ FileResponse + RFC 5987 中文文件名头
 │◄───────────────────────┤ 文件流
```

### 4.4 抖音独立通道（extractors/douyin）

抖音不走 yt-dlp，也不接受任何用户 cookie。原因与实现：

**为什么不能用 yt-dlp**

yt-dlp 的 `Douyin` 提取器报 `Fresh cookies are needed`，但这条报错是误导 —— 抖音自 2026-09-14 起对 `aweme/v1/web/aweme/detail` 加了 `x-secsdk-web-signature` 门禁：

```
HTTP 403  Blocked by ArgusSecurityPlugin Uifid Not Found
```

- 该签名**只能由抖音网页内的 SDK 生成**，纯 HTTP 客户端带不上；
- **与 cookie 无关**（社区实测：带不带都一样）；
- 手算 `a_bogus` 也不够 —— 本项目实测签名完全正确仍返回同一个 403，因为 Argus 还要 `UIFID` 设备指纹 cookie。

**解法：借浏览器签名，但不用浏览器下载**

```
POST /api/parse
  └─ media.parse_video(url)
       └─ extractors.douyin.is_douyin(url)?  ──是──▶ douyin.parse(url)
                                                        │
                          parser.extract_aweme_id(url)  │  短链 v.douyin.com 跟随重定向
                                                        ▼
                          parser.cache_get(id)  命中？ ──是──▶ 直接返回（0 秒冷启动）
                                                        │否
                                                        ▼
                          browser.fetch_aweme(id)   ← 专用 worker 线程独占 Chrome
                            · context 全新、无用户数据、无 cookie/无扩展
                            · page.goto("https://www.douyin.com/video/{id}")
                            · expect_response(匹配 /aweme/v1/web/aweme/detail/)
                            · 抖音自己的 JS 生成签名，我们只取它发出的响应 JSON
                                                        ▼
                          parser.cache_put(id, aweme)  TTL = cdn_url_expired - now
```

```
POST /api/tasks → media.run_download(url, format_id, ...)
  └─ douyin.download(...)
       ├─ parser.resolve_stream(aweme, "douyin:best") → (CDN 直链列表, ext, size)
       │    ↑ 直链实测无需 Referer、无需签名（206 + video/mp4）
       └─ downloader.download_stream(...)   ← 纯 HTTP 流式，零浏览器开销
```

**关键技术决策**

| 决策 | 理由 |
|------|------|
| 专用 worker 线程独占浏览器 | playwright 的 sync API 对象**线程绑定**，不能跨线程共享 Browser；用队列 + Future 投递任务，既复用浏览器又避开线程亲和性坑 |
| 浏览器懒启动 | 首次解析抖音才拉 Chrome。启动服务、解析 B 站完全不受影响 |
| `channel="chrome"` 复用系统 Chrome | 不下载 Chromium（省 150MB+）。按 chrome → msedge → chromium → 自带 的顺序降级 |
| **统一走 `/video/{id}` 路径** | 实测 `/note/{id}`（图集页）**不会**发出 detail 请求；`/video/{id}` 对图集同样返回完整数据（含 `images`） |
| 结果缓存 TTL 取自 `cdn_url_expired` | 直链约 3 小时失效，缓存不能比直链活得久（clamp 到 60s ~ 3h） |
| 进度回调格式与 yt-dlp `progress_hook` 同构 | `core/tasks.py` 的进度聚合、限速、速度/ETA 换算**零改动**即可复用 |

**图集（图文作品）**

- 判据：`aweme_type ∈ {2, 68}` 或 `images` 非空；
- 取 `images[].url_list`（无水印原图），**不用** `download_url_list`（带水印，`tplv-dy-water-v`）；
- 逐张下载到临时目录 → 打 zip → 删临时目录，产出 `{标题}.zip`；
- 进度按「第 N/M 张」上报，用 `_percent` 字段（多图总字节数下载前不可知）。

**平台档位语义**

抖音的 540P 档码率**常常高于** 720P 档（同一视频 540P 4.0MB / 720P 3.4MB 是常态），只按分辨率排序会误导用户。因此列表首项固定为「最佳画质」（`douyin:best`），按码率挑真正最清楚的那条；其后按分辨率降序排列各档。

## 5. API 契约

### 5.1 GET `/api/health`

```jsonc
{
  "status": "ok",
  "version": "1.0.0",
  "ffmpeg": {                     // 来自 core/ffmpeg.py 探测结果
    "available": true,
    "source": "static-ffmpeg",    // system | static-ffmpeg | imageio-ffmpeg
    "path": "/…/ffmpeg",
    "location": "/…/bin",
    "error": null
  },
  "queue": {
    "active": 1,                  // pending + downloading + merging
    "total": 3,
    "concurrency": 2,
    "threads": 9                  // 进程内线程数，用于排查线程泄漏
  }
}
```

### 5.2 POST `/api/parse`

**请求**
```jsonc
{ "url": "https://www.bilibili.com/video/BV1xxx" }   // 1..2048
```

**响应** `ParseResponse`
```jsonc
{
  "title": "…",
  "thumbnail": "https://…jpg",       // 前端须经 /api/proxy/thumbnail 取
  "duration": 137,                    // 秒
  "author": "…",
  "platform": "哔哩哔哩",              // 经 _PLATFORM_NAMES 映射为中文
  "webpage_url": "…",
  "video_id": "BV1xxx",
  "extractor": "BiliBili",
  "view_count": 123456,
  "formats": [
    {
      "id": "bestvideo[height<=1080]+bestaudio/best",  // 原样回传给创建任务接口
      "kind": "video",                // video | audio
      "label": "1080P",
      "resolution": "1920×1080",
      "height": 1080,
      "ext": "mp4",
      "fps": 60.0,
      "size": 45678901,
      "size_text": "43.6 MB",
      "has_audio": false,             // 该流单独是否带音频
      "needs_merge": true,            // 是否需要 ffmpeg 合并
      "recommended": true,
      "note": "需合并音视频"
    }
  ]
}
```

### 5.3 POST `/api/tasks`

**请求**
```jsonc
{
  "url": "https://…",
  "format_id": "bestvideo[height<=1080]+bestaudio/best",
  "title": "…",              // 可选，用于生成文件名
  "thumbnail": "https://…",  // 可选
  "quality_label": "1080P"   // 可选，仅用于展示
}
```

**响应**：`{ "task_id": "0b31d114416b4ee3", "status": "pending" }`

### 5.4 GET `/api/tasks/{task_id}`

返回 `TaskResponse`：`task_id / url / format_id / status / progress` 以及进度与产物字段（`downloaded_bytes`、`total_bytes`、`speed`、`eta`、`file_name`、`file_size_text`、`has_file`、`created_at`、`updated_at` 等）。失败时带 `error`（中文）与 `error_code`。

### 5.5 POST `/api/tasks/{task_id}/cancel`

置取消标志；下载线程捕获取消异常后把状态置为 `cancelled`。对终态任务调用是幂等的。

### 5.6 GET `/api/tasks/{task_id}/file`

返回 `FileResponse`，响应头关键是：

```
Content-Disposition: attachment; filename*=UTF-8''%E7%94%B5%E5%8A%A8%E8%BD%A6….mp4
```

中文名走 RFC 5987，**不要**退回 `filename="…"` 的裸写法，否则 Chrome 会乱码。

### 5.7 GET `/api/proxy/thumbnail?url=`

服务端代为抓取封面，规避 `Referer` 防盗链。

安全约束（`api/video.py`）：
- 白名单后缀：`.bilibili.com` `.hdslb.com` `.ytimg.com` `.ggpht.com` 等；
- 拒绝私网 / 回环 / 链路本地地址，防 SSRF；
- 按后缀注入对应 `Referer`；
- 单文件大小上限 `GOVID_THUMBNAIL_MAX_BYTES`（默认 12MB）、超时 15s。

### 5.8 统一错误体

```jsonc
{ "detail": "链接格式不对，需要以 http:// 或 https:// 开头", "code": "invalid_url" }
```

前端只依赖 `detail`（给人看）与 `code`（给程序判断）两个字段。校验失败（422）也会被翻译成中文，不透出 pydantic 英文信息。

## 6. 关键设计决策与踩坑记录

> 这一节记录**为什么这么写**。后续改动前先读这里，避免把已修复的坑再踩回去。

### 6.1 多流下载的进度聚合（计划书原文有误）

**问题**：`bestvideo+bestaudio` 是两条流分别下载。若直接读 yt-dlp 的 `_percent_str`，第二条流开始时进度会从 100% 跳回 0%，进度条来回横跳。

**解决**：按 `format_id` 分桶，累加 `downloaded_bytes` / `total_bytes`，得到单调递增的合并进度。实现见 `core/tasks.py` 的进度回调。

**推论**：任何"按 yt-dlp 百分比字符串直接展示"的写法都是错的，别回退。

### 6.2 ffmpeg 探测绝不阻塞请求路径

**问题**：static-ffmpeg 首次要从 GitHub 拉约 80MB 二进制。如果在 `ffmpeg_info()` 里同步做，一次普通下载请求会卡住好几分钟（实测 **106 秒**），且当时是在持锁状态下等网络 I/O —— 下载线程与预热线程互等，进度条永久停在 0%。

**解决**：
- 请求路径只走**本地快路径**（系统 ffmpeg → imageio-ffmpeg），立即返回；
- static-ffmpeg 由**启动时的后台线程**探测（`main.py` lifespan 里 `threading.Thread(target=ffmpeg_warmup)`）；
- 探测成功后升级 `_cached`，后续请求自动用上更好的来源。

**推论**：`ffmpeg_info()` 里不得出现任何网络 I/O。

### 6.3 ffmpeg 三级来源与 shim 目录

| 优先级 | 来源 | 说明 |
|-------|------|------|
| 1 | 系统 `ffmpeg` | `shutil.which` 找到即用，最快 |
| 2 | `static-ffmpeg` | 提供 ffmpeg + ffprobe，但二进制托管在 GitHub，网络不稳时不可靠 |
| 3 | `imageio-ffmpeg` | 二进制打包在 PyPI wheel 里，**只要 PyPI 能通就一定能拿到** |

imageio-ffmpeg 只有 ffmpeg、**没有 ffprobe**，而 yt-dlp 的 `ffmpeg_location` 需要一个**目录**且合并时会用到 ffprobe。因此在项目根建 `.bin/`，把二进制软链成标准文件名 `ffmpeg`，再把这个目录交给 yt-dlp。

**推论**：`.bin/` 是运行时产物，不要提交进版本库（已在 `.gitignore`）。

### 6.4 清晰度列表必须按分辨率归组，不能过滤 video-only 流

**问题**：计划书写「过滤无音频纯视频流」。但 YouTube / B 站的 1080P 及以上几乎全是 video-only，真过滤掉就直接看不到 1080P —— 验收标准根本达不成。

**解决**：按分辨率归组，每档生成 `bestvideo[height<=H]+bestaudio/best` 形式的合并选择器；音视频本就同流时退回单流选择器。

### 6.5 竖屏视频的档位标注

1080×1920 的竖屏视频若直接用 `height` 当档位会标成「1920P」。改为取**宽高较小的一边**作为档位，横屏 1920×1080 与竖屏 1080×1920 统一显示「1080P」。

### 6.6 Tailwind v4 不走 postcss 链路

v4 已内置 Lightning CSS 处理前缀，用官方 `@tailwindcss/vite` 插件即可。加 `postcss` + `autoprefixer` 是 v3 时代的写法，在 v4 下是多余的。

### 6.7 pydantic 校验错误要翻译

`RequestValidationError` 默认返回英文且结构冗长。`main.py` 里单独挂了处理器，把 `loc` 字段映射成中文提示，保持与业务错误一致的 `{detail, code}` 结构。

### 6.8 抖音通道踩过的坑

| 坑 | 现象 | 正解 |
|----|------|------|
| `response.url` 是属性不是方法 | `page.expect_response(pred)` 报 `'str' object is not callable` | Python 版 playwright 里 `response.url` / `response.status` 都是属性；Node 版才是 `url()` |
| `/note/{id}` 不发 detail 请求 | 图集页 `expect_response` 必然超时 | 图集也用 `/video/{id}` 打开 |
| 直接拿浏览器抓，但下载也走浏览器 | 每次下载都要起 Chrome，慢且没必要 | 浏览器只用于解析借签名；CDN 直链不校验签名，下载走纯 HTTP |
| 解析结果不缓存 | 每次解析 4 秒冷启动 | 按 `aweme_id` 缓存 JSON，TTL 跟随 `cdn_url_expired` |
| 同分辨率多档取错 | 推荐给的是低码率档 | 比较键用 `(bitrate, size)` 元组，不是插入顺序 |
| 后台进程被 shell 回收 | `nohup … & disown` 启动后服务静默消失（本次复现：服务起得来，`/api/health` 也通，但下一个命令执行前进程就没了） | **本环境下 `nohup` / `disown` 都不能逃过会话回收**，必须用工具自带的后台常驻能力启动；`curl` 访问本机端口还要加 `--noproxy '*'`，否则被沙箱代理拦成 502 |

### 6.9 前端输入校验把「分享文案」拦在门外

后端 `extract_aweme_id()` 从一开始就支持整段抖音分享文案，但**前端功能实际不可达**——这是纯接缝问题，只有在真实浏览器里点一遍才会暴露。

| 坑 | 现象 | 正解 |
|----|------|------|
| 校验正则要求**整串**是 URL | `URL_PATTERN = /^https?:\/\/[^\s]+$/i` 判定「8.88 复制打开抖音…https://… 复制此链接」不合格，解析按钮直接弹「链接格式不对」 | 新增 `extractUrl()`：纯链接原样返回，否则用 `URL_IN_TEXT` 从文本里抠出第一个 URL，再拿提取结果去校验和提交 |
| 提取后不回填 | 用户看到的仍是那一整段文案，不知道实际解析的是哪个链接 | 解析成功后把输入框回填成提取到的纯 URL |
| 提示语与能力不符 | placeholder 只写「YouTube / B 站 / Vimeo」，抖音这个唯一的自研通道反而没出现 | 统一改为「粘贴抖音 / B 站 / YouTube 等链接，或 App 分享文案…」 |

**教训**：后端能力与前端入口是两条独立链路，验收必须走真实浏览器提交，光用 `curl` 打 API 会漏掉这类「功能写着支持、用户其实用不到」的缺陷。

### 6.10 对外口径必须和文档一致

平台数在三处文案里是「1800+」，与 `docs/03-平台支持矩阵.md` 定下的 **1201 顶级站点**口径冲突；平台墙副标题还写着「不额外做私有 hack」，而抖音恰恰是自研通道。已统一修正：Hero 徽章、平台墙标题与副标题、FAQ「支持哪些平台」、`index.html` 的 SEO description 全部改为 1201 口径，并显式说明抖音走独立通道。

### 6.11 本机环境备忘

- 启动常驻服务用工具自带的后台能力，不要用 `nohup`（见 6.8 最后一行）。
- 本机端口健康检查必须 `curl --noproxy '*'`：沙箱注入的 `HTTP_PROXY` 会把 `127.0.0.1:8000` 也代理走，服务没起时返回的是代理的 `502 upstream connect failed`，容易误判成服务异常。

### 6.12 平台墙为什么不用 CSS animation

需求是「鼠标悬停时**减速**而不是停止」。CSS 做不到这件事：

- `animation-play-state: paused` → 直接停住，不是减速；
- 改 `animation-duration` → 动画进度按新时长重算，**画面会跳位置**（负 `animation-delay` 补偿需要 JS 逐帧算，等于把逻辑搬到 JS）。

所以平台墙改成 `requestAnimationFrame` 驱动 `translate3d`，速度用指数平滑逼近目标值：

```js
factors[i] += (targetFactor - factors[i]) * Math.min(1, dt * EASE)  // EASE = 6，约 200ms 收敛
let next = offsets[i] + dir * BASE_SPEED * factors[i] * dt
if (next <= -half) next += half   // 位移循环在 (-half, 0]，配合「内容复制两份」实现无缝
if (next > 0) next -= half
```

要点：`half` 取 `scrollWidth / 2`（而不是硬编码宽度），保证字体与图片加载完后仍然无缝；开了 `prefers-reduced-motion` 就完全不启动 rAF。

实测：常速 33 px/s → 悬停 9 px/s（≈0.28 倍），松开平滑回到常速。

### 6.14 分享到微信后「点下载没反应」（真机反馈的坑）

用 `share.sh` 把服务分享出去后，亲友反馈「怎么点下载都没反应」，但服务端任务明明跑完了、文件也在 `tmp/` 里。排查结论：**链路没问题，是 App 内置浏览器的兼容问题**。

先用 curl 直连隧道域名验证：`HTTP 200`、字节数正确、`content-type: video/mp4`、文件是合法 MP4 —— 说明服务端与隧道都正常，问题只在客户端。

两个根因：

| 坑 | 现象 | 正解 |
|----|------|------|
| 只发 `filename*=UTF-8''…` | 微信 / QQ 内核（X5、WKWebView）**不认 RFC 5987**，遇到这种 Content-Disposition 会当作没有该头处理 → 点击变成「在页面里播视频」或干脆无响应 | 同时发 `filename="ASCII 回退"` 与 `filename*=…`。纯中文标题折叠后为空时退回 `govid-<任务号8位>.ext`，保证旧内核用户也能拿到能识别的文件名 |
| `<a download>` 在 App 内置浏览器里无效 | 这是内核限制，前端无法绕过 | 加 `target="_blank" rel="noopener"`，让内核降级成「新窗口打开」，再由服务端的 `attachment` 头触发下载；同时按 UA 检测内置浏览器（微信 / QQ / 微博 / 支付宝 / 钉钉 / 抖音），进页面就显示「点右上角 ⋯ → 在浏览器打开」的引导，下载卡片下方再提示一次 |

`share.sh` 打印分享地址时也会带上这句提醒，方便直接转述给亲友。

**教训**：`<a download>` + `Content-Disposition: filename*` 这套在桌面 Chromium 上完美，但**真机微信才是最可能出现问题的环境**。分享类功能至少要按 UA 覆盖一次内置浏览器场景，否则「桌面测通了」会给出错误的通过结论。

## 7. 环境、配置与运行

### 7.1 为什么用内存队列

阶段 1-2 是**单机自用**：并发是 1-2，任务生命周期是分钟级，进程重启后残留任务本来也该作废（临时文件会被清空）。引入 Redis/Celery 只会增加部署复杂度而不解决任何真实问题。

**升级触发条件**：多实例部署 / 需要任务持久化 / 需要跨进程调度 —— 三者任一出现，再换。

### 7.2 配置项（`.env`，前缀 `GOVID_`）

| 变量 | 默认 | 说明 |
|------|------|------|
| `GOVID_HOST` | `0.0.0.0` | 监听地址（默认允许局域网访问） |
| `GOVID_PORT` | `8000` | 端口 |
| `GOVID_RELOAD` | `false` | 热重载 |
| `GOVID_DOWNLOAD_DIR` | `<root>/tmp` | 临时下载目录 |
| `GOVID_MAX_CONCURRENT_DOWNLOADS` | `2` | 并发下载数，超出排队 |
| `GOVID_SOCKET_TIMEOUT` | `30` | 网络超时（秒） |
| `GOVID_TASK_TTL_HOURS` | `2` | 任务与文件保留时长 |
| `GOVID_MAX_TMP_GB` | `20` | tmp 目录占用上限，超出按最旧回收；`0` 关闭 |
| `GOVID_MAX_FORMATS` | `15` | 清晰度档位上限 |
| `GOVID_PROXY` | 空 | 出网代理，如 `http://127.0.0.1:7890` |
| `GOVID_COOKIES_FILE` | 空 | Netscape 格式 cookies.txt，**阶段 3 用** |
| `GOVID_FRONTEND_DIST` | `<root>/frontend/dist` | 前端产物路径 |
| `GOVID_THUMBNAIL_TIMEOUT` | `15` | 封面抓取超时 |
| `GOVID_THUMBNAIL_MAX_BYTES` | `12582912` | 封面大小上限 |

### 7.3 启动流程（`run.sh`）

```
检查 python / node
   └─ 有 conda 用 conda，没有则用项目内 .venv（幂等创建）
检查依赖是否齐全（import 探测）
   └─ 缺则 pip install -e ../yt-dlp[default] + -r backend/requirements.txt
检查 frontend/dist 是否存在
   └─ 缺或 --rebuild 则 npm install + npm run build
取本机 IP
启动 uvicorn
```

参数：`--dev`（后端 reload + Vite dev server）、`--skip-build`、`--rebuild`。

### 7.4 启动时会发生什么（`main.py` lifespan）

1. `purge_download_dir()`：清空 `tmp/`，避免上次残留占盘。
2. `reset_tasks()`：清空内存任务字典（进程重启后旧任务本就不该存在）。
3. `start_reaper()`：启动后台线程，每 5 分钟执行 `cleanup_expired()` + `enforce_disk_quota()`。
4. 启动 `govid-ffmpeg-warmup` 守护线程异步探测 ffmpeg。

### 7.5 临时文件的完整生命周期（用户常问）

成品文件**不会永久留在服务器上**，四条路径覆盖所有情况：

| 时机 | 行为 | 实现 |
|------|------|------|
| 服务启动 | 清空整个 `tmp/` | `purge_download_dir()` |
| 任务终结（完成/失败/取消）后超过 TTL | 删记录 + 删文件 + 删任务目录 | `cleanup_expired()`，TTL 默认 2 小时 |
| `tmp/` 总占用超过 `GOVID_MAX_TMP_GB` | 按最旧优先回收，直到降到上限的 80% | `enforce_disk_quota()`，**跳过仍在下载的任务** |
| 进程退出 | 内存任务表随进程消失，下次启动走第 1 条 | `_tasks` 是进程内字典 |

前端在下载完成卡片上直接告诉用户「这份文件会在 N 小时后自动清掉」（N 取自 `/api/health` 的 `task_ttl_hours`），省得用户惦记着去手动清理。

**为什么需要配额兜底**：TTL 只管「单个任务别留太久」。如果 2 小时内涌进几十个大文件（4K 视频动辄 1-2GB），单靠 TTL 仍可能把磁盘写满。配额是第二道闸，两者互补。

### 7.6 临时公网分享（给亲友试用，免备案）

`./share.sh` 用 Cloudflare 快速隧道把本机端口映射成公网 https 地址。

```
./run.sh      # 一个终端跑服务
./share.sh    # 另一个终端跑隧道 → 打印 https://xxxx.trycloudflare.com
```

- **不需要备案**：备案针对中国大陆境内服务器；快速隧道不落地任何服务器，流量经境外 Cloudflare 边缘回源到本机。
- 不需要 Cloudflare 账号、域名、公网 IP、路由器端口映射。
- 地址每次重启会变；要固定地址需要自有域名 + 命名隧道。
- 代价：本机必须保持开机，服务与隧道都不能关。
- 脚本会自动下载 `cloudflared` 到 `.bin/`（首次约 19MB），起隧道前先探活本机服务，没起会直接提示。

实测（2026-09-21）：隧道建立后从公网请求 `/api/health` 返回 `200`，`task_ttl_hours: 2` 正常透出。

**复用点**：字幕获取天然需要复用 `core/media.py` 的 yt-dlp 选项构造与 `core/ffmpeg.py`；不要另起一套。

### 10.2 阶段 4：用户系统与付费

- 引入 SQLite（起步）→ PostgreSQL（上量）：新增 `backend/db/`、`backend/models/user.py`。
- JWT 认证：`api/auth.py` + 依赖注入式的 `current_user`。
- 配额：在 `core/tasks.py` 的 `create_task()` 入口做检查，**不要**散落到各接口。
- **必须先做**：TD-1（CORS）与 TD-5（cookies），否则对外服务既危险又难用。

### 10.3 阶段 5：生产化

Dockerfile（多阶段构建：node 构建前端 → python 运行后端）、Nginx 反代与 HTTPS、Prometheus 指标、Sentry 错误追踪。

### 10.4 新增一个 API 的固定动作

1. `models/video.py` 加请求/响应模型（或新建 `models/xxx.py`）。
2. `core/` 里实现业务逻辑，**不要**写在路由函数里。
3. `api/xxx.py` 写路由，只做参数校验 + 调 core + 返回模型。
4. `main.py` 里 `app.include_router(xxx.router, prefix="/api")`。
5. 新增错误类型时，在 `core/errors.py` 加类 + 中文文案 + `translate_error` 映射。
6. README 的 API 表同步更新。
