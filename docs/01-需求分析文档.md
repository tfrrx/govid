## 1. 项目背景与定位

### 1.1 背景

现有视频下载工具（在线解析站、浏览器插件、命令行 yt-dlp）存在三类问题：

| 现状 | 痛点 |
|------|------|
| 在线解析站 | 广告多、限速、需要扫码登录、隐私不可控（链接被记录） |
| 浏览器插件 | 安装门槛、权限过大、跨平台覆盖差 |
| yt-dlp 命令行 | 能力最强但需要记参数、看进度条要开终端、无法给非技术用户用 |

### 1.2 定位

**本机运行、零广告、有图形界面的视频下载器**，把 yt-dlp 的解析能力包装成「粘贴链接 → 选清晰度 → 下载」三步。

一句话：*yt-dlp 的能力 + 在线工具的上手门槛*。

### 1.3 三条不可动摇的产品原则

1. **本地优先**：视频流不经过第三方服务器，数据不出本机（除解析请求本身）。
2. **不做专用 hack**：平台支持完全依赖 yt-dlp 官方解析器，不维护私有逆向代码。
3. **能跑就够**：阶段 1-2 不引入数据库 / 消息队列 / 用户系统，避免过度设计。

## 2. 目标用户与使用场景

### 2.1 用户画像

| 类型 | 特征 | 核心诉求 |
|------|------|---------|
| 主用户：本人 | macOS，有技术背景，厌恶广告与登录 | 快速拿到文件，看清进度，能取消 |
| 次要用户：同 Wi-Fi 的设备 | 手机 / 平板浏览器 | 不用装 App，扫码级别的使用门槛 |
| 远期用户：内容整理者 | 需要 AI 总结、字幕、思维导图 | 下载只是入口，价值在后续加工 |

### 2.2 核心使用场景

**SC-1 桌面下载（主场景）**
> 在电脑上刷到 B 站视频，想存下来离线看。打开 `localhost:8000`，粘贴链接，选 1080P，看到进度条走完，点下载。

**SC-2 手机下载（同 Wi-Fi）**
> 手机浏览器打开 `http://<电脑IP>:8000`，同样流程。要求布局不崩、按钮可点。

**SC-3 失败可诊断（重要）**
> 链接贴错 / 平台不支持 / 网络不通时，**必须看到中文人话说明**，而不是白屏或英文堆栈。

**SC-4 中途放弃**
> 发现选错了清晰度或不想下了，能一键取消，不能只能等它跑完。

**SC-5（待开发）看完即总结**
> 下载完成后，直接在同一页面拿到 AI 摘要、字幕、思维导图，不用再跳工具。

## 3. 功能需求

> 状态图例：✅ 已实现并验收 · 🔶 已实现未验收 · ⬜ 未开始

### 3.1 FR-1 视频解析

| 编号 | 需求 | 验收标准 | 状态 |
|------|------|---------|------|
| FR-1.1 | 用户可粘贴视频链接或 App 分享文案并发起解析 | 输入框支持回车提交与按钮提交；整段分享文案能自动提取出链接并在解析后回填为纯 URL | ✅ |
| FR-1.2 | 解析结果含标题、封面、时长、作者、平台、播放量 | 字段全部返回且正确（B 站实测） | ✅ |
| FR-1.3 | 封面图可正常显示 | 经后端代理绕过防盗链，不出现裂图 | ✅ |
| FR-1.4 | 解析期间有加载态 | 显示骨架屏，不是空白等待 | ✅ |
| FR-1.5 | 平台名可识别并展示 | 展示 yt-dlp 识别出的站名 | ✅ |

### 3.2 FR-2 清晰度选择

| 编号 | 需求 | 验收标准 | 状态 |
|------|------|---------|------|
| FR-2.1 | 列出全部可选清晰度 | 至少覆盖 1080P / 720P / 480P / 360P | ✅ |
| FR-2.2 | 每档显示分辨率、体积、格式、帧率 | 体积缺失时显示「未知」而非空白 | ✅ |
| FR-2.3 | 默认选中最佳画质 | 首屏即推荐项，且标注「推荐」 | ✅ |
| FR-2.4 | 支持仅音频导出 | 末位提供 MP3 选项 | ✅ |
| FR-2.5 | 竖屏视频档位标注正确 | 1080×1920 显示「1080P」而非「1920P」 | ✅ |
| FR-2.6 | 档位数量有上限 | 默认最多 15 档，避免列表过长 | ✅ |

> **设计权衡**：高画质档（1080P+）在 YouTube / B 站几乎都是 video-only 流，必须与音频轨合并。因此**不能按「过滤无音频流」的朴素做法实现**，否则 1080P 直接消失。正确做法是按分辨率归组 + 自动拼接合并选择器。详见技术文档 §6。

| 编号 | 需求 | 验收标准 | 状态 |

| FR-3.1 | 提交下载任务后返回任务 ID | 立即返回，不阻塞在下载上 | ✅ |

| FR-3.4 | 分段进度可视化 | 解析 → 下载 → 合并 三步状态可见 | ✅ |
| FR-3.5 | 可取消下载 | 取消后任务终止且状态置为已取消 | ✅ |

| FR-3.7 | 过期任务自动回收 | 超时任务与临时文件被清理 | ✅ |

## 4. 非功能需求

### 4.1 性能

| 编号 | 指标 | 目标 | 实测 |
|------|------|------|------|
| NFR-P1 | 页面首屏加载 | < 2s | ✅ 达标 |
| NFR-P2 | 解析响应时间 | < 5s | ⚠️ 受源站影响，B 站约 1-3s |
| NFR-P3 | 首次启动（含依赖安装） | < 3 分钟 | ⚠️ 网络差时超时，靠幂等重跑 |
| NFR-P4 | 进度刷新间隔 | 1s | ✅ |

### 4.2 兼容性

| 编号 | 要求 |
|------|------|
| NFR-C1 | 桌面 Chrome / Safari 布局正常 |
| NFR-C2 | 移动端浏览器（390×844 基准）无横向溢出 |
| NFR-C3 | macOS 与 Linux 可运行；Windows 未验证 |
| NFR-C4 | ffmpeg 不存在时自动降级，不报错退出 |

### 4.3 可用性与无障碍

- 关键操作有加载态与禁用态，避免重复提交。
- FAQ 折叠面板满足键盘可达（`aria-expanded` / `aria-controls`）。
- 颜色对比度按浅色主题校验。
- 表单错误在输入框附近与 Toast 双通道提示。

### 4.4 安全

| 编号 | 要求 | 状态 |
|------|------|------|
| NFR-S1 | 缩略图代理做 SSRF 防护（拒私网/回环/本地域名） | ✅ |
| NFR-S2 | 静态资源路径穿越防护 | ✅ |
| NFR-S3 | CORS 当前全放开（本机自用），对外部署必须收紧 | ⚠️ 技术债 |
| NFR-S4 | 无用户数据上传 | ✅ |
| NFR-S5 | 不存储任何账号凭据 | ✅ |

### 4.5 可维护性

- 后端单模块单职责，`core/` 不依赖 `api/`。
- 错误类型集中在 `core/errors.py`，新增平台报错只需加映射规则。
- 设计 Token 集中在 `frontend/src/style.css` 的 `@theme`，不散落硬编码色值。
- 配置项集中在 `.env`，代码里不写死。

| D-08 | 动效强度 | 适度微交互 250-350ms | 有质感但不拖慢 | 无动画 / 重动画 |
| D-09 | 定价策略 | 轻量保守占位 | 功能未就绪，不承诺做不到的事 | 直接上付费墙 |
| D-10 | 平台支持范围 | 以 yt-dlp 官方解析器为主，被风控封死的平台另建独立通道 | 不维护私有逆向，长期可维护 | 全部自研解析（成本爆炸） |
| D-11 | ffmpeg 获取 | 自动获取，三级来源 | 用户不该手动装 ffmpeg | 要求用户自行安装 |
| D-12 | 错误处理 | 统一 Toast + 中文翻译 | 降低非技术用户挫败感 | 直接透出 yt-dlp 原始报错 |
| D-13 | 任务队列 | 进程内字典 + 线程 | 阶段 1-2 零依赖即可满足 | 引入 Celery / Redis |
| D-14 | 前后端通信 | 轮询 1s | 实现简单、可断线重连 | WebSocket / SSE |
| D-15 | 环境管理 | conda 优先，缺省回落 venv | 兼容没有 conda 的机器 | 硬依赖 conda |
| D-16 | 部署方式 | `run.sh` 一键脚本 | 本机自用，无需容器 | 一开始就上 Docker |
| D-17 | CSS 方案 | Tailwind v4 | 原子化 + 设计 Token 集中管理 | 手写 CSS / UI 库 |
| D-18 | 抖音支持 | 独立通道 `extractors/douyin`：无痕浏览器借签名 + 纯 HTTP 下载 | `aweme/detail` 已被 `x-secsdk-web-signature` 门禁封死，yt-dlp 与手算 a_bogus 均返回 403；用户明确要求必须支持抖音 | 要求用户提供 cookie（用户明确拒绝）；依赖第三方解析 API（不可控） |
| D-19 | 抖音图集 | 支持，打包 zip 下载原图 | 图文作品占比高，「不支持图集」约等于「不支持抖音」 | 只支持视频作品 |
| D-20 | 抖音档位排序 | 首项固定「最佳画质」（按码率选），其后按分辨率降序 | 抖音 540P 档码率常高于 720P，只按分辨率排序会误导用户 | 单纯按分辨率排序 |
| D-21 | 前端输入校验 | 先用 `extractUrl()` 从文本中提取链接，再校验与提交；解析成功后把输入框回填为纯 URL | 后端本就支持整段分享文案，前端若坚持「整串必须是 URL」会让该能力实际不可达（D-18 承诺的便利打了折） | 只接受纯 URL 输入 |
| D-22 | 平台数量口径 | 对外统一「1201 个顶级站点」，抖音单独说明为自研通道 | 前端文案原写 1800+，与 `docs/03` 定下的保守口径冲突；且抖音不走 yt-dlp，「基于 yt-dlp」的说法不完整 | 沿用 1800+ 含子项的行业口径 |

## 6. 明确不做的事

> 写清楚边界，比写清楚需求更能防止范围蔓延。

1. **不做平台专用逆向**。某平台失效时，正确动作是升级 yt-dlp，而不是写补丁。
2. **不绕过 DRM 与付费墙**。VIP / 会员内容不支持是设计约束，不是缺陷。
3. **不做在线服务**。不提供公共托管版本，避免版权与带宽风险。
4. **不内置下载历史与账号体系**（阶段 4 前）。
5. **不追求全部 1800+ 平台的 100% 可用率**。yt-dlp 自身对部分站点标注 `CURRENTLY BROKEN`，本项目不承诺覆盖。
6. **不做移动端原生 App**。浏览器访问即可。
